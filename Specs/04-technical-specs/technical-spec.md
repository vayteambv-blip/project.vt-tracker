# Технические Спеки

Этот файл описывает техническую структуру проекта на первом этапе, когда система остается frontend-only.
Бизнес-логика из `Global Spec` и `Functional Map` здесь не меняется, а только переводится в техническую форму.

## 1. Архитектура

- приложение должно быть веб-приложением с адаптацией под телефон и компьютер;
- интерфейс должен быть модульным и строиться по смысловым блокам;
- все данные должны опираться на стабильные идентификаторы и связи между сущностями;
- технические решения не должны добавлять новые продуктовые правила;
- пока проект остается frontend-only, техническая архитектура должна быть готова к дальнейшему расширению без изменения бизнес-логики.

## 2. Главные источники данных

### 2.1 Клиент

Клиент бывает двух типов:

- частный клиент;
- фирма-заказчик.

Клиент хранит:

- тип клиента;
- имя или название;
- фамилию или контактное лицо;
- телефон;
- email;
- адрес;
- связанные проекты.

### 2.2 Фирма

Фирма хранит:

- данные фирмы;
- документы фирмы;
- контракты фирмы;
- текущих рабочих;
- историю рабочих;
- обзор проектов фирмы.

Фирма не хранит:

- отдельный финансовый блок;
- материалы;
- фотографии;
- отчеты.

Фирма может быть:

- фирмой-исполнителем;
- фирмой-заказчиком.

### 2.3 Проект

Проект является основной рабочей единицей системы.
Один проект соответствует одной работе и одному направлению.

Проект хранит:

- клиент;
- направление работ;
- адрес;
- статус проекта;
- дату старта;
- дату окончания, если она есть;
- диапазон рабочих дней;
- связанные фирмы;
- документы проекта;
- стартовые фото объекта;
- фото процесса;
- фото в отчетах;
- отчеты;
- материалы;
- финансы;
- связь с календарем;
- архивную связь.

### 2.4 Документы

Документы делятся на два уровня хранения:

- документы проекта;
- документы фирмы.

Отдельно хранится совместный документ `фактура`, который виден и в проекте, и в фирме как одна общая синхронизированная сущность с одной историей версий.
Отдельно хранятся шаблоны как черновики для проекта и фирмы.

Документ хранит:

- тип;
- текущий файл;
- архивные версии;
- контекст: проект, фирма или общая фактура;
- действие отправки документа на email;
- возможность открыть и скачать файл из карточки.

Шаблон хранит:

- набор обязательных полей;
- тип основы: проект или фирма;
- черновой статус без автозаполнения.

### 2.5 Отчеты

Отчет хранит:

- заголовок;
- текст;
- фотографии отчета;
- дату создания;
- дату изменения;
- связь с проектом.

### 2.6 Материалы

Материал хранится только внутри проекта и содержит:

- название;
- количество;
- единицы;
- отметку закуплено.

### 2.7 Финансы

Финансы хранят денежные строки по проекту.

Финансовые категории:

- подготовка и сдача объекта;
- материалы;
- оплата фирмам;
- аренда техники;
- непредвиденные расходы.

Дополнительно в финансах хранятся:

- базовая смета;
- дополнительные работы как отдельная строка проекта;
- итог по оплатам фирмам;
- остаток до оплаты;
- итоговая прибыль.

### 2.8 Календарь

Календарь не хранит отдельные работы, а отображает только проекты.
В интерфейсе календарь показывается по направлениям работ, но данные хранятся как одна система записей с фильтром по направлению.
Каждый проект должен быть виден в календаре каждый день в пределах своего диапазона рабочих дней.

Календарь хранит:

- проект;
- дату старта;
- дату окончания, если она задана;
- список всех фирм, которые участвуют в проекте;
- календарную группу `текущий` или `будущий`;
- связь с направлением работ.

### 2.9 Архив

Архив хранит только завершенные проекты.

Архив хранит:

- проект как завершенную запись;
- поисковые поля по году;
- поисковые поля по месяцу;
- поисковые поля по разделу;
- поисковые поля по клиенту.

### 2.10 Админ

Админская логика хранит:

- основной аккаунт главного администратора;
- приглашение нового администратора по email;
- ссылку-приглашение;
- подтверждение от главного администратора;
- активацию полного доступа после подтверждения.

## 3. Связи между сущностями

- один клиент может иметь много проектов;
- один проект связан только с одним клиентом;
- один проект может иметь несколько фирм;
- одна фирма может участвовать в нескольких проектах;
- связь проект - фирма должна хранить роль фирмы в проекте: `executor` или `customer`;
- документы проекта и документы фирмы хранятся отдельно;
- фактура является одной общей синхронизированной сущностью между проектом и фирмой с одной историей версий;
- материалы, фотографии и отчеты принадлежат только проекту;
- календарная запись создается из проекта;
- архивная запись создается из завершенного проекта;
- рабочий принадлежит только одной фирме.

## 4. Состояния и переходы

### 4.1 Статус проекта

У проекта есть четыре ручных статуса:

- `подготовка`;
- `первый этап`;
- `второй этап`;
- `сдача`.

Статус проекта меняется вручную.

### 4.1.1 Допустимые значения

Для технической реализации используются фиксированные значения:

- тип клиента: `private`, `company_customer`;
- направление проекта: `roof`, `facade`, `interior`, `global_construction`;
- статус проекта: `preparation`, `stage_1`, `stage_2`, `handover`;
- календарная группа: `future`, `current`;
- тип фотографии: `start`, `process`, `report`;
- категория расхода: `prep_handover`, `materials`, `firm_payments`, `equipment_rent`, `unforeseen`;
- тип файла: `estimate`, `project_contract`, `firm_contract`, `facture`, `act`, `additional_work`, `other`;
- состояние версии файла: `current`, `archived`.

### 4.2 Календарные состояния

В календаре используются только две рабочие группы:

- `будущий` - проект запланирован, но еще не начат;
- `текущий` - проект уже идет.

Это календарные группы, а не отдельные статусы проекта.

### 4.3 Переход дат

- если дата старта задана в проекте, она должна появляться в календаре;
- если дата старта меняется в календаре, она должна обновляться в проекте;
- если меняется дата старта, вместе с ней должен сдвигаться весь диапазон рабочих дней;
- если дата старта отсутствует, проект не показывается в календаре;
- перенос даты не должен ломать связи проекта.

### 4.4 Архивирование

- завершенный проект переносится в архив вручную;
- из архива проект возвращается вручную;
- если проект возвращается из архива, он продолжается как тот же самый проект, а не как новый;
- при возврате из архива у проекта снова выбирается новая дата старта;
- архив не смешивается с текущими проектами;
- архив всегда должен оставаться отдельным блоком.
- в архиве должен открываться полный проект на момент закрытия;

### 4.5 Создание проекта

- для создания проекта нужна заранее согласованная смета;
- если смета не одобрена, проект не считается готовым к созданию;
- остальные документы можно добавлять позже.

## 5. Хранение и версии файлов

- все файлы должны иметь текущую версию;
- старые версии должны сохраняться как архив;
- архивных версий может быть несколько;
- старые версии можно открыть и скачать;
- старую версию можно восстановить как текущую;
- файл нельзя удалять без следа, только заменять и архивировать;
- в общем списке по умолчанию показываются только текущие файлы;
- фильтры должны работать по типам файлов;
- типы файлов должны оставаться плоскими, без отдельных подпапок.

## 6. Правила синхронизации

### 6.1 Проект и календарь

- проект является главным источником календарной даты;
- календарь показывает проект, а не отдельные работы;
- если в проекте несколько фирм, календарь показывает их все списком;
- клик по календарной записи открывает проект с полной карточкой и всей нужной информацией;
- календарь не должен дублировать лишние данные;
- дата старта должна быть общей для проекта и календарного отображения.

### 6.2 Проект и фирма

- документы проекта и фирмы хранятся отдельно;
- фактура хранится как одна общая синхронизированная сущность с одной историей версий;
- если фактуры обновляются, изменения видны в проекте и в фирме;
- если документ относится только к проекту, он не должен появляться в фирме автоматически;
- если документ относится только к фирме, он не должен появляться в проекте автоматически;
- материалы, фотографии и отчеты не синхронизируются в фирму.

### 6.3 Финансы и оплатa фирм

- оплата фирм всегда идет через расходы проекта;
- у фирмы нет отдельного финансового блока;
- итог по оплатам фирм считается внутри проекта;
- прибыль считается как базовая смета плюс дополнительные работы минус все расходы.

### 6.4 Уведомления

- для проекта с назначенной датой старта должно быть напоминание за 10 рабочих дней и повтор за 5 рабочих дней;
- уведомление должно поддерживать email и WhatsApp как отдельные каналы доставки;
- уведомление привязано к проекту и календарной дате старта;
- уведомления не должны дублировать календарь и не должны создавать отдельный рабочий блок.

## 7. Техническая структура экранов

Технически приложение должно поддерживать отдельные рабочие экраны:

- клиент;
- фирма;
- проект;
- календарь;
- финансы;
- отчеты;
- документы;
- архив.

Каждый экран показывает только свою часть данных и не должен создавать лишние копии информации.

## 8. Именование, пустые состояния и фильтры

- все видимые названия должны быть понятными для пользователя;
- внутренние коды и enum-значения должны использоваться только в технической части;
- для пустых списков нужны понятные empty states с короткой подсказкой, что добавить дальше;
- сообщения об ошибках должны показывать, какое поле не заполнено и в какой сущности, и подсвечивать это заметно;
- если не хватает нескольких вещей, должен быть короткий список того, чего именно не хватает;
- рядом с ошибкой должна быть короткая подсказка, что именно нужно добавить или исправить;
- если обязательные данные не заполнены, сохранение или переход дальше должны быть заблокированы до исправления;
- для создания клиента, фирмы и проекта должны быть определены минимально обязательные поля, без которых сохранение запрещено;
- уже введенные данные не должны теряться при обновлении страницы, если форма еще не завершена;
- если страница обновилась, уже введенные данные должны остаться на месте;
- при создании клиента или фирмы интерфейс должен также блокировать сохранение до заполнения обязательных полей;
- при создании проекта интерфейс должен сразу показывать, чего не хватает, и блокировать сохранение до исправления;
- старые версии документов должны быть доступны для открытия и скачивания;
- если документ меняется, старая версия остается в истории и не теряется;
- у документа должно быть не больше 2 старых версий, и они должны быть быстро доступны для открытия;
- старую версию нужно открывать прямо из карточки документа без долгого поиска;
- в карточке документа должно быть сразу понятно, где текущая версия, а где старые версии;
- если документ относится и к проекту, и к фирме, старые версии должны быть видны в обоих местах;
- в карточке проекта должны сразу отображаться все фирмы, которые участвуют в проекте;
- итог по проекту должен храниться и отображаться в финансах, а не дублироваться в карточке проекта;
- в списке проектов должны быть видны название и статус;
- если проект заполнен не до конца, это состояние должно быть заметно сразу;
- внутри проекта должен быть быстрый обзор фирм, документов, отчетов и материалов;
- фильтры и поиск должны менять только отображение, а не данные;
- длинные списки должны быстро находиться через поиск и фильтры;
- длинные списки должны быть просматриваемыми через фильтры и понятные разделы;
- после поиска должен быть быстрый переход в нужную карточку;
- в интерфейсе в приоритете быстрый просмотр и скачивание, а история версий доступна как дополнительная функция;
- технические названия файлов и внутренних состояний не должны попадать в пользовательский интерфейс.

## 9. Ограничения

- не добавлять новые продуктовые сущности;
- не вводить скрытые дубли данных;
- не смешивать фирму, клиента и проект;
- не делать календарь второй базой данных;
- не делать архив копией текущих проектов;
- не переносить в техспек уже закрытые бизнес-правила без необходимости;
- не расширять структуру файла лишними разделами без повода.

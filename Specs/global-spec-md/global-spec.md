# Бизнес-контекст

Этот файл фиксирует всю общую логику проекта до перехода к Functional Spec.

## 1. Суть проекта

- Проект создается для строительной компании в Бельгии.
- Основной пользователь - я, как главный администратор.
- На первом этапе это только фронтенд-сайт.
- Сайт должен удобно работать и на телефоне, и на компьютере.
- Проект нужен для полного контроля, управления и организации строительных проектов.
- Проект должен экономить время на управлении и планировании.

## 2. Что решает проект

Проект нужен для того, чтобы я мог:

- видеть все проекты;
- видеть текущие, будущие и завершенные проекты;
- быстро понимать, какие проекты идут сейчас, какие начнутся позже, а какие уже завершены;
- планировать сроки и работы;
- отслеживать расходы;
- хранить документы, фото, контакты и файлы;
- вести периодические отчеты по этапам проекта;
- хранить архив завершенных проектов;
- быстро находить нужный проект по разделам и году;
- видеть финансовую картину по каждому проекту, клиенту и фирме;
- контролировать оплату и задолженности;
- хранить данные по фирмам и клиентам в одном месте;
- работать без лишнего дублирования и мусора;
- использовать шаблоны и аналитику по прибыли уже сейчас.

## 3. Термины проекта

- Проект - это основная строительная единица.
- Клиент - это заказчик проекта.
- Клиент бывает двух типов:
  - фирма-заказчик;
  - частный клиент.
- Термин `работы` не используется как отдельная сущность в базе.
- Слово `работы` используется только как обычное описание процесса.
- У проекта есть только три статуса:
  - будущий;
  - в процессе;
  - завершенный.

## 4. Что должно быть видно на уровне смысла

Проект должен уметь:

- показывать проекты, которые будут в будущем;
- показывать проекты, которые сейчас в процессе;
- показывать завершенные проекты;
- показывать список проектов, которые скоро начнутся;
- показывать выполнение проекта в календаре и в списке проектов;
- показывать фирмы, которые будут исполнять работу;
- помогать планировать следующие шаги;
- экономить время на управлении и организации;
- поддерживать комментарии внутри проекта.

## 5. Клиенты

Для каждого клиента нужно хранить:

- имя;
- налоговый номер;
- адрес;
- телефонный номер;
- email;
- документы;
- связанные проекты.

Клиент должен храниться как отдельная сущность.

## 6. Типы клиентов

Клиенты бывают двух типов:

- фирма-заказчик;
- частный клиент.

Для частного клиента нужно хранить:

- имя;
- налоговый номер;
- адрес проживания;
- телефонный номер;
- email;
- документы;
- связанные проекты.

Для фирмы-клиента нужно хранить:

- имя;
- налоговый номер;
- адрес фирмы;
- телефонный номер;
- email;
- документы;
- связанные проекты.

## 7. Фирмы

- Один проект может иметь несколько фирм.
- Разные фирмы могут выполнять разные работы на одном проекте.
- На одном проекте возможны разные комбинации работ.
- В проекте я только прикрепляю нужную фирму.
- У фирмы должна быть отдельная страница со всеми ее данными.
- У фирмы нужно хранить все файлы, документы и информацию отдельно.
- У фирмы нужно хранить рабочих, которые к ней привязаны.
- Рабочие всегда привязаны к определенной фирме.
- История участия фирм в проектах не нужна.

Для каждой фирмы нужно хранить:

- имя;
- налоговый номер;
- адрес фирмы;
- телефонный номер;
- email;
- документы;
- рабочие, которые к ней привязаны;
- отдельные файлы и информация по фирме.

## 8. Рабочие

- Рабочие всегда прикреплены к определенной фирме.
- Рабочие могут меняться внутри фирмы.
- История рабочих внутри фирмы не нужна.
- История рабочих в проектах не нужна.

## 9. Проекты

- Для каждого проекта обязательно хранить:
  - дату старта;
  - дату окончания, если она уже известна;
  - текущий статус;
  - адрес проекта, где исполняется работа.
- Дата старта обязательна всегда.
- Дата окончания может быть пустой, пока проект еще не завершен.
- У проекта может быть несколько фирм.
- У проекта хранятся связанные документы, фото, отчеты, календарь и расходы.

## 10. Работы и направления

Работы делятся на четыре основных направления:

- кровля и строительство крыш;
- фасады;
- внутриотделочные работы;
- глобальная стройка, строительство домов и каркасов.

На одном проекте могут быть разные комбинации работ:

- кровля и фасад;
- фасад и внутриотделочные работы;
- кровля и внутриотделочные работы;
- любые другие нужные сочетания.

Отдельные записи работ в базе не нужны.
Работа должна отображаться через:

- календарь;
- список проектов;
- отчеты по этапам;
- прикрепленные фирмы и рабочих.

## 11. Расходы

По каждому проекту нужно видеть расходы отдельно.

Типы расходов:

- материалы;
- фактуры фирм, которые выполняют работу;
- зарплаты;
- мелкие расходы;
- непредвиденные расходы.
- показывать итог по каждому проекту;
- показывать итог по клиенту;
- показывать итог по фирме;
- делать общий финансовый обзор;
- делать финальный подсчет в конце проекта.

## 12. Финансовая логика

Для каждого проекта важно видеть:

- общий итог по проекту;
- сумму, которая уже оплачена;
- сумму, которая еще не оплачена;
- полный итог в конце проекта.

По клиенту нужен итог.
По фирме нужен итог.
Аналитика по прибыли = сметная цена минус все расходы.

## 13. Календарь

- Календарь показывает только проекты.
- Нужны два отдельных календаря:
  - для текущих проектов;
  - для будущих проектов.
- В календаре должно быть видно:
  - старт проекта;
  - возможную дату окончания проекта.
- В каждом календаре всегда должна быть возможность добавить фирму, которая будет исполнять работу.
- Для проекта, который должен начаться, нужны уведомления за 10 рабочих дней до старта.
- Через календарь я должен сверять текущие и будущие проекты.

## 14. Периодические отчеты

- Периодические отчеты делает только я.
- Отчет нужен для фиксации прогресса проекта.
- Отчеты помогают видеть этапы проекта:
  - подготовительные работы;
  - работы в процессе;
  - сдача проекта.

В каждый отчет входят:

- короткое описание;
- дата;
- 2-3 фотографии максимум;
- отметка, на каком этапе находится проект.

## 15. Комментарии внутри проекта

- Комментарии внутри проекта нужны для записи этапов проекта.
- Каждый комментарий может содержать:
  - текст;
  - 1 или несколько фотографий.
- Комментарии помогают фиксировать, на каком процессе находится проект.

## 16. Документы и файлы

По каждому проекту нужно хранить:

- смету;
- контракт;
- фактуры;
- акты сдачи;
- фото;
- контакты клиента;
- другие нужные файлы по проекту.

Смета и фактуры могут храниться как PDF-файлы.
Другие нужные файлы - это любые дополнительные материалы по проекту, например чертежи, сканы, дополнительные документы или прикрепленные файлы.

У фирмы свои документы и файлы хранятся отдельно.
У клиента свои документы и файлы хранятся отдельно.
На проекте я прикрепляю нужные данные, а не дублирую все вручную.

## 17. Шаблоны и аналитика

Проект должен поддерживать:

- шаблоны проектов;
- шаблоны фирм;
- аналитику по прибыли;
- комментарии внутри проекта.

Шаблон - это заготовка с нужными полями и данными, которую можно использовать как основу для проекта или фирмы.

Это нужно не потом, а уже в рамках текущего проекта.

## 18. Контакты

Контакты нужны для:

- клиентов;
- фирм;
- проектов.

Для контактов клиента и фирмы нужны:

- имя;
- налоговый номер;
- телефонный номер;
- email;
- адрес.

## 19. Архив

- Нужно хранить архив завершенных проектов.
- Архив должен быть отдельным блоком.
- Архив должен быть удобно отсортирован по годам.
- В архиве я должен быстро выбирать нужный год, раздел и клиента.
- Архив должен открываться и быть доступным для поиска по разделам и клиентам.
- Разделы в архиве - это 4 направления работ:
  - кровля и строительство крыш;
  - фасады;
  - внутриотделочные работы;
  - глобальная стройка, строительство домов и каркасов.

## 20. Четыре уровня хранения

### 1. Глобально в системе

На верхнем уровне хранятся:

- клиенты;
- проекты;
- фирмы;
- рабочие;
- документы;
- фото;
- календарь;
- расходы;
- отчеты;
- архив;
- шаблоны;
- комментарии.

### 2. Внутри проекта

У каждого проекта хранятся:

- клиент;
- связанные фирмы;
- расходы;
- документы;
- фото;
- календарь;
- отчеты;
- комментарии;
- статус проекта;
- дата начала;
- дата окончания, если она уже известна;
- адрес проекта;
- итог по проекту;
- оплата и сумма, которая уже закрыта;
- статус оплаты: оплачено или не оплачено.

### 3. Внутри фирмы

У каждой фирмы хранятся:

- имя;
- налоговый номер;
- адрес фирмы;
- телефонный номер;
- email;
- документы;
- рабочие, которые к ней привязаны;
- отдельные файлы и информация по фирме;
- шаблоны, если они нужны для этой фирмы.

### 4. Внутри клиента

У каждого клиента хранятся:

- имя;
- налоговый номер;
- адрес;
- телефонный номер;
- email;
- документы;
- связанные проекты;
- тип клиента: фирма-заказчик или частный клиент;
- для частного клиента отдельно хранится адрес проживания;
- для фирмы-клиента отдельно хранится адрес фирмы;
- шаблоны и документы, если они относятся к клиенту.

## 21. Доступ

- Роли доступа сейчас не нужны.
- Сейчас полный доступ есть только у меня.
- В будущем можно будет добавить любое количество админов с полным доступом.
- Дополнительные админы должны иметь такой же доступ, как и у меня.

## 22. Важное ограничение

- На первом этапе проект остается только фронтендом.
- Ничего лишнего и дублирующегося добавлять не нужно.
- Все описания должны быть короткими, понятными и по делу.

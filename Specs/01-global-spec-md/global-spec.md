# Бизнес-контекст

Этот файл фиксирует общую логику проекта до перехода к Functional Spec.

## 1. Суть проекта

- Проект создается для строительной компании в Бельгии.
- Основной пользователь - я, как главный администратор.
- На первом этапе это только фронтенд-сайт.
- Сайт должен удобно работать и на телефоне, и на компьютере.
- Проект нужен для контроля, управления и организации строительных проектов.
- Проект должен экономить время на управлении и планировании.

## 2. Что решает проект

- видеть текущие, будущие и завершенные проекты;
- понимать статус каждого проекта без лишнего поиска;
- планировать сроки и этапы;
- отслеживать расходы;
- хранить документы, фото, контакты и файлы;
- вести короткие периодические отчеты по этапам;
- хранить архив завершенных проектов;
- быстро находить нужный проект по году, разделу и клиенту;
- видеть финансовую картину и прибыль;
- контролировать оплату и задолженности;
- работать без лишнего дублирования и мусора;
- использовать шаблоны уже сейчас.

## 3. Термины проекта

- Проект - это основная строительная единица.
- Клиент - это заказчик проекта.
- Термин `работы` не используется как отдельная сущность в базе.
- Слово `работы` используется только как общее описание этапа, вида работ или процесса.
- У проекта есть только три статуса:
  - будущий;
  - в процессе;
  - завершенный.

## 4. Типы клиентов

Клиенты бывают двух типов:

- фирма-заказчик;
- частный клиент.

Для каждого клиента данные хранятся отдельно в зависимости от его типа.

Для частного клиента хранится:

- имя;
- налоговый номер;
- адрес проживания;
- телефон;
- email;
- документы;
- связанные проекты.

Для фирмы-заказчика хранится:

- имя;
- налоговый номер;
- адрес фирмы;
- телефон;
- email;
- документы;
- связанные проекты.

Фирма-заказчик - это генеральный заказчик.

## 5. Фирмы и рабочие

- Разные фирмы могут выполнять разные виды работ на одном проекте.
- На одном проекте возможны разные комбинации работ.
- В проекте я только прикрепляю нужную фирму.
- У фирмы должна быть отдельная страница со всеми ее данными.
- У фирмы нужно хранить все файлы, документы и информацию отдельно.
- У фирмы нужно хранить рабочих, которые к ней привязаны.
- Рабочие всегда привязаны к определенной фирме.
- История участия фирм в проектах не нужна.
- История рабочих внутри фирмы и в проектах не нужна.

## 6. Проекты

- Для каждого проекта обязательно хранить:
  - дату старта;
  - дату окончания, если она уже известна;
  - текущий статус;
  - адрес проекта.
- Дата старта обязательна всегда.
- Дата окончания может быть пустой, пока проект еще не завершен.
- Статус проекта задается отдельно и может меняться вручную, когда мне это нужно.
- У проекта хранятся связанные документы, фото, отчеты, календарь и расходы.
- Все эти данные привязаны к карточке проекта и открываются внутри него.

## 7. Виды работ

Работы делятся на четыре основных направления:

- кровля и строительство крыш;
- фасады;
- внутриотделочные работы;
- глобальная стройка, строительство домов и каркасов.

На одном проекте возможны разные сочетания этих направлений.

Отдельные записи работ в базе не нужны.
Работа показывается через:

- календарь;
- список проектов;
- отчеты по этапам;
- прикрепленные фирмы и рабочих.

## 8. Расходы и финансы

По каждому проекту нужно видеть расходы отдельно.

Типы расходов:

- материалы;
- фактуры фирм;
- мелкие расходы;
- непредвиденные расходы.

Проект должен уметь:

- показывать итог по каждому проекту;
- показывать итог по фирме;
- делать финальный подсчет в конце проекта.

Аналитика по прибыли = сметная цена минус все расходы.

## 9. Календарь

- Нужны отдельные календари по каждому направлению работ:
  - кровля;
  - фасады;
  - внутриотделочные работы;
  - глобальная стройка.
- В каждом календаре должно быть видно:
  - подготовленные проекты;
  - проекты в процессе;
  - завершенные проекты до переноса в архив;
  - дату старта проекта;
  - возможную дату окончания проекта.
- В каждом календаре должна быть возможность добавить фирму, которая будет исполнять работу.
- Для проекта, который должен начаться, нужны уведомления за 10 рабочих дней до старта.
- Календарь должен открываться по месяцам.
- В календаре я должен видеть, какой проект стартует в конкретный день.
- Я должен иметь возможность перенести старт проекта на другую дату.
- Через календарь я должен видеть обзор по каждому направлению и дате старта проекта.

## 10. Периодические отчеты и комментарии

- Периодические отчеты делаю только я.
- Отчет нужен для фиксации прогресса проекта.
- В каждом отчете:
  - короткое описание;
  - дата;
  - фотографии без ограничения по количеству.

## 11. Документы и файлы

По каждому проекту нужно хранить:

- смету;
- контракт;
- фактуры;
- акты сдачи;
- фото;
- контакты клиента;
- другие нужные файлы и документы по проекту без ограничений по типу.

Смета и фактуры могут храниться как PDF-файлы.
Другие нужные файлы - это любые файлы и документы без ограничений по типу.

У каждого клиента свои документы и файлы хранятся отдельно, в зависимости от типа.

## 12. Шаблоны

Проект должен поддерживать:

- шаблоны проектов;
- шаблоны фирм.

Шаблон - это заготовка с нужными полями и данными, которую можно использовать как основу для проекта или фирмы.

Автозаполнение не нужно.

## 13. Архив

- Нужно хранить архив завершенных проектов.
- Архив должен быть отдельным блоком.
- Архив должен быть удобно отсортирован по годам.
- В архиве я должен быстро выбирать нужный год, раздел и клиента.
- Архив должен открываться и быть доступным для поиска.
- Разделы в архиве - это 4 направления работ:
  - кровля и строительство крыш;
  - фасады;
  - внутриотделочные работы;
  - глобальная стройка, строительство домов и каркасов.

## 14. Четыре уровня хранения

- Глобально в системе: клиенты, проекты, фирмы, рабочие, документы, фото, календарь, расходы, отчеты, архив, шаблоны, комментарии.
- Внутри проекта: клиент, связанные фирмы, расходы, документы, фото, календарь, отчеты, комментарии, статус, даты, адрес, итог, оплата.
- Внутри фирмы: данные фирмы, документы, рабочие, отдельные файлы и информация.
- Внутри клиента: данные клиента, документы, связанные проекты и тип клиента.

## 15. Доступ

- Сейчас полный доступ есть только у меня.
- В будущем можно будет добавить любое количество админов с полным доступом.
- Дополнительные админы должны иметь такой же доступ, как и у меня.

## 16. Важное ограничение

- На первом этапе проект остается только фронтендом.
- Ничего лишнего и дублирующегося добавлять не нужно.
- Все описания должны быть короткими, понятными и по делу.

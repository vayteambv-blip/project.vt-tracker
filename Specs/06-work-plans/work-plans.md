# Work Plans

Этот файл хранит активные рабочие планы текущего этапа. Первый план закрывается сейчас, второй запускается только после его завершения.

## 1. Статус

- активная рабочая фаза открыта;
- первый план идет сейчас;
- второй план ждет завершения первого;
- при изменении правил сначала сверяются связанные спеки, затем код.

## 2. Первый план на сегодня

### Шаг 1. Зафиксировать текущее состояние

- посмотреть, что уже изменено в коде;
- отделить готовое от черновиков;
- сверить изменения с текущими спеками;
- понять, что уже можно считать базой для продолжения.

Результат шага:
- есть короткая картина текущего состояния;
- понятно, какие части уже можно не трогать;
- видны места, где еще есть расхождения.

### Шаг 2. Привести документы к единой логике

- проверить `Specs/02-functional-map-md/*` на дубли и расхождения;
- проверить `Specs/04-technical-specs/technical-spec.md` на совпадение с текущими правилами;
- все будущие уточнения оставить в `Specs/03-future-spec-md/future-spec.md`;
- все текущие задачи и очередность работ держать в этом файле;
- не переносить уже закрытые правила повторно.

Результат шага:
- спеки не спорят между собой;
- понятно, что относится к текущей фазе, а что к следующей;
- в документации нет лишних повторов.

### Шаг 3. Довести самый полезный рабочий кусок в коде

- привести основные экраны и общие компоненты к единому поведению;
- проверить ключевые связи между блоками;
- отдельно пройтись по проекту, календарю, архиву, документам и финансам;
- убедиться, что изменения не ломают базовую логику.

Результат шага:
- рабочая часть проекта становится цельной;
- ключевые переходы между разделами ведут себя одинаково;
- можно безопасно продолжать следующий слой работы.

### Шаг 4. Финальная проверка первого плана

- проверить, что нет конфликтов между спеками;
- проверить, что нет потери данных и связей;
- проверить, что календарь, архив и проект работают по одной логике;
- зафиксировать, что осталось на следующий этап.

Результат шага:
- есть понятный итог дня;
- ясно, что закрыто;
- ясно, что переносится дальше.

## 3. Порядок выполнения первого плана

1. Сначала фиксируется текущее состояние.
2. Потом приводятся в порядок документы.
3. Затем закрывается самый полезный кусок в коде.
4. После этого делается короткая проверка результата.

## 4. Что не делать в первом плане

- не добавлять новые сущности без отдельного подтверждения;
- не смешивать текущую работу с будущими правилами;
- не дублировать уже зафиксированные положения в других местах без необходимости;
- не переносить в следующий этап то, что уже должно остаться в текущей базе.

## 5. Второй план

Этот план начинается только после полного завершения первого плана.

### Шаг 1. Подготовить `Future Spec`

- оставить только будущие уточнения и расширения;
- убрать все, что уже относится к текущей функциональной карте;
- проверить, что нет дублей с `Global Spec` и `Functional Map`;
- зафиксировать только то, что действительно нужно для следующего этапа.

Результат шага:
- `Future Spec` содержит только следующий слой развития;
- текущие правила не повторяются;
- будущие идеи отделены от уже закрытых положений.

### Шаг 2. Подготовить `Technical Spec`

- привести технические решения к текущей и будущей логике без новых бизнес-правил;
- проверить, что техслой не спорит с функциональной картой;
- отметить только то, что нужно для реализации следующего этапа;
- убрать лишние повторения и случайные детали.

Результат шага:
- технический слой готов к следующему этапу;
- структура остается простой и связанной с правилами;
- техспек не дублирует другие документы.

### Шаг 3. Подготовить `User Stories`

- переписать сценарии так, чтобы они совпадали с обновленными спеками;
- оставить только пользовательские пути, которые реально нужны для работы;
- убрать сценарии, которые уже закрыты или не относятся к текущей базе;
- проверить, что истории читаются как единый набор действий пользователя.

Результат шага:
- пользовательские истории совпадают с правилами и техникой;
- нет лишних повторов;
- сценарии удобно использовать для следующего этапа работ.

### Шаг 4. Сверка второго плана

- проверить, что `Future Spec`, `Technical Spec` и `User Stories` не спорят между собой;
- убедиться, что все три файла идут в одной логике;
- отметить, что можно передавать в реализацию следующего этапа;
- зафиксировать, что именно готово к запуску после первого плана.

Результат шага:
- второй план полностью подготовлен;
- переход между планами ясен;
- следующий этап можно запускать без пересборки структуры.

# Технические Спеки

Этот файл описывает техническую структуру проекта на первом этапе, когда система остается frontend-only. Бизнес-логика из `Global Spec` и `Functional Map` здесь не меняется, а только переводится в техническую форму.

## Активный режим второго плана

- этот файл активируется после завершения первого плана из `Work Plans`;
- технические решения здесь должны следовать уже согласованным правилам и подготовке к следующему этапу;
- не добавлять новые бизнес-правила через техническое описание;
- сначала проверять связку с `Functional Map`, потом фиксировать техрешение.

## 1. Архитектура

- приложение должно быть веб-приложением с адаптацией под телефон и компьютер;
- интерфейс должен быть модульным и строиться по смысловым блокам;
- все данные должны опираться на стабильные идентификаторы и связи между сущностями;
- технические решения не должны добавлять новые продуктовые правила;
- пока проект остается frontend-only, архитектура должна быть готова к дальнейшему расширению без изменения бизнес-логики.

## 2. Главные источники данных

### 2.1 Клиент

Клиент бывает двух типов:

- частный клиент;
- клиент-фирма.

Клиент хранит:

- тип клиента;
- для частного клиента:
  - имя;
  - фамилию;
  - телефон;
  - email;
  - адрес проживания;
- для клиент-фирмы:
  - название;
  - телефон;
  - email;
  - адрес;
  - налоговый номер;
- связанные проекты.

Для частного клиента адрес означает адрес проживания.
Для клиент-фирмы адрес означает адрес компании, а налоговый номер обязателен.

### 2.2 Субподрядчик

Субподрядчик хранит:

- имя;
- роль;
- статус;
- количество рабочих;
- количество проектов;
- путь оплаты.

Субподрядчик не хранит:

- отдельный финансовый блок;
- материалы;
- фотографии;
- отчеты;
- отдельную историю документов и сопутствующих файлов.

Субподрядчик может быть только исполнителем.

### 2.3 Проект

Проект является основной рабочей единицей системы.
Один проект соответствует одной работе и одному направлению.

Проект хранит:

- клиент;
- направление работ;
- адрес;
- статус проекта;
- дату старта;
- диапазон рабочих дней;
- связанные субподрядчики;
- документы проекта;
- отчеты;
- материалы;
- финансы;
- связь с календарем;
- архивную связь.

### 2.4 Документы

Документы делятся на два уровня хранения:

- документы проекта;
- документы субподрядчика.

Документ хранит:

- название;
- контекст: проект, субподрядчик или связанный документ;
- номер версии;
- заметку;
- метку последнего изменения.

### 2.5 Отчеты

Отчет хранит:

- заголовок;
- текст;
- фотографии отчета;
- дату создания;
- дату изменения;
- связь с проектом.

Фотографии хранятся только внутри отчетов.
Отдельного архива старых фото нет.

### 2.6 Материалы

Материал хранится только внутри проекта и содержит:

- название;
- количество;
- единицы;
- отметку закуплено.

### 2.7 Финансы

Финансы хранят денежные строки по проекту.

Финансовые категории:

- подготовка и сдача объекта;
- материалы;
- оплата субподрядчикам;
- аренда техники;
- непредвиденные расходы.

Дополнительно в финансах хранятся:

- базовая смета;
- дополнительные работы оформляются как отдельный проект со своей согласованной сметой, а не как строка в финансах проекта;
- итог по оплатам субподрядчикам;
- остаток до оплаты;
- итоговая прибыль.

### 2.8 Календарь

Календарь не хранит отдельные работы, а отображает только проекты.
В интерфейсе календарь показывается по направлениям работ, но это один календарь без разделения на разные календарные экраны.
Каждый проект должен быть виден в календаре каждый день в пределах своего диапазона рабочих дней.

Календарь хранит:

- проект;
- дату старта;
- несколько субподрядчиков, которые участвуют в проекте;
- календарную группу `draft`, `ready`, `active`, `archive`;
- связь с направлением работ.

Технически:

- `draft` означает проект без даты старта;
- `ready` означает проект, у которого уже есть дата старта, но старт еще не наступил;
- `active` означает проект, который уже стартовал;
- `archive` означает завершенный проект.

### 2.9 Архив

Архив хранит только завершенные проекты.

Архив хранит:

- проект как завершенную запись;
- поисковые поля по году;
- поисковые поля по месяцу;
- поисковые поля по разделу;
- поисковые поля по клиенту.

## 3. Связи между сущностями

- один клиент может иметь много проектов;
- один проект связан только с одним клиентом;
- один проект может иметь несколько субподрядчиков;
- субподрядчики могут участвовать в нескольких проектах;
- связь проект - субподрядчик должна хранить роль субподрядчика в проекте: `executor`;
- документы проекта и документы субподрядчика хранятся отдельно;
- денежные записи субподрядчика проходят через расходы проекта и не хранятся отдельным блоком;
- отчеты принадлежат только проекту, а фотографии хранятся внутри отчетов;
- внутри проекта есть отдельный вход в финансовый обзор, где видны расходы проекта;
- календарная запись создается из проекта;
- архивная запись создается из завершенного проекта;
- рабочий принадлежит только одному субподрядчику.

## 4. Состояния и переходы

### 4.1 Статус проекта

У проекта есть четыре ручных статуса:

- `подготовка`;
- `первый этап`;
- `второй этап`;
- `сдача`.

Статус проекта меняется вручную.

### 4.1.1 Допустимые значения

Для технической реализации используются фиксированные значения:

- тип клиента: `Private`, `Business`;
- направление проекта: `roof`, `facade`, `interior`, `rough_construction`;
- статус проекта: `preparation`, `stage_1`, `stage_2`, `handover`;
- календарная группа: `draft`, `ready`, `active`, `archive`;
- категория расхода: `prep_handover`, `materials`, `subcontractor_payments`, `equipment_rent`, `unforeseen`;
- контекст документа: `Project`, `Subcontractor`, `Linked`.

### 4.2 Календарные состояния

В календаре используются четыре рабочие группы:

- `черновик` - проект еще не готов к запуску, но его уже можно сохранить с недостающими полями;
- `готовые к запуску` - проект уже имеет дату старта, но старт еще не наступил;
- `активный` - дата старта наступила;
- `архив` - проект завершен.

Это календарные группы, а не отдельные статусы проекта.

### 4.3 Переход дат

- дата старта синхронизируется между проектом и календарем в обе стороны;
- при изменении даты старта сдвигается весь диапазон рабочих дней;
- если даты старта нет, проект не показывается в календаре;

### 4.4 Архивирование

- завершенный проект переносится в архив вручную;
- из архива проект возвращается вручную как тот же проект с новой датой старта;
- архив остается отдельным блоком и открывает проект целиком на момент закрытия;

### 4.5 Создание проекта

- проект считается полностью заполненным, когда есть название, данные проекта, данные клиента, адрес, email, телефон и согласованная смета;
- если обязательных данных не хватает, система показывает недочеты и позволяет сохранить черновик;

- для создания проекта нужна заранее согласованная смета;
- если смета не одобрена, проект не считается готовым к созданию;
- смета проекта не меняется со временем;
- если появляется дополнительная работа, создается отдельный проект со своей согласованной сметой;
- остальные документы можно добавлять позже.

## 5. Хранение и версии файлов

- важные документы в текущем слое хранятся как текущие записи без отдельного архива версий;
- файл нельзя удалять без следа, только редактировать или удалять запись;
- в общем списке по умолчанию показываются только текущие записи;
- типы файлов не делятся на подпапки.

## 6. Правила синхронизации

### 6.1 Проект и календарь

- проект является главным источником календарной даты;
- календарь показывает проект, а не отдельные работы;
- календарь показывает только связанных с проектом субподрядчиков;
- клик по календарной записи открывает проект с полной карточкой и всей нужной информацией;
- календарь не должен дублировать лишние данные;
- дата старта должна быть общей для проекта и календарного отображения.

### 6.2 Проект и субподрядчик

- документы проекта и субподрядчика хранятся отдельно по контексту;
- связанные документы не смешиваются автоматически с проектными или субподрядными;
- материалы и отчеты не синхронизируются в субподрядчика.

### 6.3 Финансы и оплата субподрядчика

- оплата субподрядчика всегда идет через расходы проекта;
- у субподрядчика нет отдельного финансового блока;
- итог и прибыль считаются внутри проекта.

### 6.4 Уведомления

- для проекта с датой старта есть напоминания за 10 и 5 рабочих дней на сайте;
- уведомления привязаны к проекту и календарной дате старта;
- уведомления не дублируют календарь и не создают отдельный рабочий блок.

## 7. Техническая структура экранов

Технически приложение должно поддерживать отдельные рабочие экраны:

- клиент;
- субподрядчик;
- проект;
- календарь;
- финансы;
- отчеты;
- документы;
- архив.

Каждый экран показывает только свою часть данных и не должен создавать лишние копии информации.

## 8. Именование, пустые состояния и фильтры

- все видимые названия должны быть понятными для пользователя;
- внутренние коды и enum-значения должны использоваться только в технической части;
- для пустых списков нужны понятные empty states с короткой подсказкой, что добавить дальше;
- сообщения об ошибках должны показывать, какое поле не заполнено и в какой сущности, и подсвечивать это заметно;
- если не хватает нескольких вещей, должен быть короткий список того, чего именно не хватает;
- рядом с ошибкой должна быть короткая подсказка, что именно нужно добавить или исправить;
- если обязательные данные не заполнены, система показывает, что именно нужно дописать, и сохраняет запись как черновик;
- для создания клиента, субподрядчика и проекта должны быть определены минимально обязательные поля, при этом запись можно сохранить как черновик до полного заполнения;
- уже введенные данные не должны теряться при обновлении страницы, если форма еще не завершена;
- если страница обновилась, уже введенные данные должны остаться на месте;
- при создании клиента или субподрядчика интерфейс должен сразу показывать, чего не хватает, и позволять сохранить черновик;
- при создании проекта интерфейс должен сразу показывать, чего не хватает, и позволять сохранить черновик;
- в карточке документа видно название, контекст, версию и заметку;
- в карточке проекта должны сразу отображаться связанные субподрядчики;
- итог по проекту должен храниться и отображаться в финансах, а не дублироваться в карточке проекта;
- в списке проектов должны быть видны название и статус;
- если проект заполнен не до конца, это состояние должно быть заметно сразу;
- внутри проекта должен быть быстрый обзор субподрядчиков, документов, отчетов и материалов;
- фильтры и поиск должны менять только отображение, а не данные;
- длинные списки должны быстро находиться через поиск и фильтры;
- длинные списки должны быть просматриваемыми через фильтры и понятные разделы;
- после поиска должен быть быстрый переход в нужную карточку;
- в интерфейсе в приоритете быстрый просмотр текущей записи, а история версий относится к будущему этапу;
- технические названия файлов и внутренних состояний не должны попадать в пользовательский интерфейс.

## 9. Ограничения

- не добавлять новые продуктовые сущности;
- не вводить скрытые дубли данных;
- не смешивать субподрядчика, клиента и проект;
- не делать календарь второй базой данных;
- не делать архив копией текущих проектов;
- не переносить в техспек уже закрытые бизнес-правила без необходимости;
- не расширять структуру файла лишними разделами без повода.

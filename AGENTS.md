# Инструкции для Codex

Этот репозиторий подготовлен для работы с Codex.

## Общие правила

- Вся документация ведется на русском языке.
- Названия файлов и папок должны быть понятными и единообразными.
- Не смешивать служебные файлы, требования и функциональные описания в одну папку без необходимости.
- Перед добавлением новой структуры сначала проверять, не ломает ли она уже заданную иерархию.

## Обязательная проверка полноты

При создании или изменении следующих сущностей всегда проверять, что заполнены все нужные поля, документы и файлы:

- проект;
- фирма;
- клиент.

Для проекта особенно проверять:
- название проекта;
- данные самого проекта;
- данные клиента;
- адрес;
- email;
- номер телефона;
- смета, заранее одобренная клиентом;
- дату старта как единую точку истины:
  - ее можно задать в проекте или в календаре;
  - изменение в одном месте должно автоматически обновляться в другом;
  - если даты старта нет, проект не показывается в календаре.

Для клиента особенно проверять:
- имя;
- фамилию;
- адрес проживания;
- телефон;
- email;
- клиентские документы не требуются.

Для фирмы особенно проверять:
- смету или предложение по работе, если фирма выступает как субподрядчик;
- текущий глобальный контракт по сотрудничеству;
- налоговый номер;
- адрес фирмы;
- телефон;
- email;
- документы и рабочие.

Если чего-то не хватает, Codex должен явно сообщать о пропусках.

При каждом создании или изменении проекта, клиента или фирмы-исполнителя Codex должен:

- проверить полноту данных;
- сделать короткий анализ на недочеты;
- явно показать, какие поля, документы или файлы не заполнены;
- не считать запись готовой, пока не указаны все обязательные данные.

## Правила ситуаций

Если в проекте еще нет даты старта:
- проект остается в списке будущих проектов;
- проект не показывается в календаре;
- статус `будущий` сохраняется.

Если создается проект:
- у него только один клиент;
- фирм у проекта может быть несколько;

Если дата старта задана в проекте или в календаре:
- дата синхронизируется в обе стороны;
- проект появляется в нужном календаре по направлению работ;
- проект переходит из будущих в планируемые для календаря.

Если у проекта появляются расходы:
- расходы хранятся только в финансах;
- в проекте расходы не дублируются.

Если добавляется новый документ:
- старый файл остается как архивная версия;
- текущим считается новый файл;
- по умолчанию показывается только текущая версия.

Если у файла есть архивная версия:
- ее можно открыть, скачать, переименовать и восстановить;
- для файла хранится только одна архивная версия.

Если фирма участвует в проекте:
- роль и вид работ задаются на уровне проекта;
- фирма не хранит постоянную специализацию;
- детали участия не дублируются отдельно в карточке фирмы.

Если используется календарь:
- в нем показываются только проекты;
- отдельные задачи и отдельные работы туда не добавляются.

Если документ относится к клиенту:
- его не сохраняют как отдельный тип хранения;
- клиентские документы в проекте не ведутся.

Если документ относится к проекту или фирме:
- он хранится только в соответствующей карточке;
- у файла есть только текущая версия и одна архивная версия;
- по умолчанию показывается только текущая версия;
- архивная версия открывается по запросу.

Если документ нужно отправить:
- его можно отправить на email прямо из карточки файла.

Если отчет создан:
- у отчета должен быть заголовок;
- отчет сортируется по дате создания;
- отчет можно редактировать и удалять.

Если отчет создан:
- в нем может быть несколько фотографий;
- фотографии привязываются к самому отчету.

Если проект завершен:
- его можно вручную перенести в архив;
- при необходимости его можно вручную вернуть обратно.

Если сущность меняется и затрагивает больше одного спека:
- Codex проверяет все связанные спеки;
- Codex выравнивает формулировки, чтобы не было дублей и противоречий.

Если проект имеет расходы:
- они хранятся только в финансах;
- в проекте расходы не дублируются.

Если возникает сомнение или серая зона:
- не додумывать самому;
- сначала показать пользователю спорный момент;
- только после подтверждения вносить правило.

## Правило порядка

- Структура проекта всегда должна идти в том же порядке, что и утвержденная схема.
- Основной порядок блоков не менять:
  - `.agents/skills/pilot-spec-workflow`
  - `Specs`
  - `06-work-plans`
- Если добавляются новые разделы, они должны вставляться только в логически правильное место и не ломать порядок.

## Правило чистоты структуры

- Не создавать дублирующиеся файлы и папки с одинаковым смыслом.
- Не хранить несколько версий одного и того же спека в разных местах.
- Не оставлять лишние `README.md`, временные файлы, пустые папки и мусорные заготовки.
- Любая новая структура должна быть минимальной, понятной и без повторений.

## Текущая структура проекта

- `.agents/skills/pilot-spec-workflow/SKILL.md` - инструкция по работе со спецификациями и правилами проекта.
- `Specs/01-global-spec-md/global-spec.md` - общий контекст, цели, ограничения, терминология.
- `Specs/02-functional-map-md/functional-map.md` - описание функций проекта.
- `Specs/03-future-spec-md/future-spec.md` - следующий этап после функциональной карты.
- `Specs/04-technical-specs/technical-spec.md` - техническая теория и решения.
- `Specs/05-user-stories/user-stories.md` - пользовательские истории и сценарии.
- `06-work-plans/active/work-plans.md` - активные планы работ.
- `06-work-plans/inactive/template-plan.md` - шаблон для отложенных планов.

## Формат работы

- Для основных спеков использовать отдельные `.md`-файлы внутри `Specs`.
- Технические спеки хранить отдельно внутри `Specs/04-technical-specs`.
- Все изменения делать аккуратно, чтобы структура оставалась простой и внятной.
